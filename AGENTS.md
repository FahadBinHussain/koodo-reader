## premium unlock: how the fork is structured (READ FIRST)

**dev = upstream/dev + ONE infra commit + nothing else.** the source changes are NOT committed to dev. they live ONLY in `patches/premium-unlock.patch` and get applied at build time:

- `patches/premium-unlock.patch` — the single canonical patch (all customizations)
- `patches/apply-patch.js` — idempotent apply script: checks for marker strings in `src/utils/request/user.ts`, applies `git apply` if not present, skips if present
- `patches/sync-upstream.ps1` — future upstream merge workflow (fetch → reset to upstream → verify patch applies → apply)
- `package.json` scripts:
  - `premium:apply` → `node patches/apply-patch.js`
  - `premium:revert` → `git checkout -- <all 15 patched files>` (manager.tsx, common.ts, configUtil.ts, thirdparty.ts, user.ts, bookUtil.ts, viewer/component.tsx, pages/reader/component.tsx, coverUtil.ts, popupTrans/component.tsx, dialogs/deleteDialog/component.tsx, importLocal/component.tsx, containers/header/component.tsx, storage/databaseService.ts, storage/syncService.ts — keep this list in sync with the patch when it grows)
  - `prebuild` AND `build` both run `node patches/apply-patch.js` so Vercel deploys the patched code automatically
- `.gitattributes` — `*.patch text eol=lf` (CRITICAL: a CRLF patch file breaks `git apply` on Windows; PowerShell `>` / `Set-Content` writes CRLF. write patch files via `git show <rev>:patches/premium-unlock.patch` piped through python, or normalize with `.Replace("\`r\`n","\`n")`)

### IMPORTANT behavioral gotchas (learned the hard way)

1. **Koodo Sync toggle MUST be OFF - and sync now refuses to run while it is on.** when `isEnableKoodoSync=yes`, the site reads sync data from Koodo's own server (`cloudtest.960960.xyz`), not from the MEGA data source. with no real auth the server returns `invalid params`, and `getSyncData` falls back to the `koodo_sync_data_<type>` localStorage snapshots **when they exist** (written by `updateSyncData` while the toggle was on) or to empty storage. stale snapshots are the dangerous case: they still contain rows the data source deleted (verified on desktop: `koodo_sync_data_books` holds row `1772101991973`, `koodo_sync_data_sync` holds its `save` record time 1787905292926), so the merge **re-pulls ghost rows from the device's own snapshot on every sync** — symptom: "the number appears after sync, gone before sync" while the cloud is verifiably clean (the 2026-10-10 phone ghost). cloud-only books also never pull from MEGA while it is on. fix on the device: Settings → Sync and backup → turn OFF "Enable Koodo Sync" → sync once (then the data source's `delete` record beats the local save and the ghost row is removed). `beforeSync` now aborts loudly (toast + throw `"Enable Koodo Sync is on; refusing to sync from stale local snapshots"`, bundle marker `refusing to sync from stale local snapshots`) when the toggle is on, and the first-sync "Enable Koodo Sync" offer dialog was removed so nothing turns it back on. this is not a bug - Koodo Sync fundamentally can't work without real auth, so OFF is correct for this fork. diagnosis on a suspect device: `JSON.parse(localStorage.readerConfig).isEnableKoodoSync` + presence of `koodo_sync_data_*` keys.
2. **"Adding" toast hanging forever** = `encryptToken` server call returns `{"code":400,"msg":"invalid params"}` because `Authorization: Bearer` is empty (no real Pro token). the patch now catches the bundled-lib TypeError and falls back to local storage, so MEGA/webdav bind works offline.
3. **"Synchronization failed, error code: invalid params"** = `getSyncData`/`updateSyncData` hitting Koodo's server. patch falls back to local storage. if this reappears, verify the configUtil.ts patch is applied.
4. **"Decryption failed, error code: invalid params"** = `decryptToken` trying to decrypt a stored token through the server. patch returns raw JSON tokens directly when they lack the `#` marker.
5. **testConnection "Connection failed" for MEGA in browser** = megajs Blob upload is unreliable in browser. patch skips the real upload test for MEGA and returns true.
6. **Vercel deploy must run the patch**: `build` script is `node patches/apply-patch.js && react-scripts build` — verify a deployed bundle contains `koodo_sync_data` / `9999999999` strings to confirm the patch applied at build time (comments get stripped; check code strings not comments).
7. **"Book not exists" on EVERY book click (2026-08-28)** = upstream added an `is_authed` token gate in `redirectBook` (`src/utils/file/bookUtil.ts`). the premium patch only forces Redux auth state (`handleFetchAuthed`), NOT the `is_authed` token, so the gate short-circuits all cloud downloads → "Book not exists" toast. fix: patch drops the `is_authed` check and just tests `isBookExistInCloud`. if this reappears after an upstream merge, verify `bookUtil.ts` is in the patch and the gate is gone.
8. **blank page + blank gray cover (2026-08-28, same book)** = two NULL fields in books.db. (a) `description` NULL → `pages/reader/component.tsx render()` calls `.indexOf("scanned")` → React render() throws → whole reader page silently unmounts = blank. (b) `cover` NULL → `coverUtil.isCoverExist` does `book.cover !== ""` → `null !== ""` is TRUE → renders `<img src={null}>` = broken gray box, never falls back to the format+name EmptyCover. both fixed in the patch (NULL-safe) AND in the MEGA data (set `description=''`, `cover=''`). **never insert a book with NULL description or cover — use empty strings.**
9. **web "Restore library" hangs forever** = `restore()` calls `window.electronAPI` (restore.ts:189) which only exists in the desktop app. on web it never resolves → stuck "Restoring..." dialog. it's desktop-only; hard-refresh to clear, and DON'T use Restore on web. on web, fresh library data is pulled by the automatic sync on load (header `handleCloudSync`) — to force it, just reload the page.
10. **Official AI Translation is blank / never works (2026-08-28)** = it's a server-side paid Koodo feature. `getTransStream` → `ReaderRequest.getTransFetch` → POST `/api/v1/pro/reader/get_llm_trans_stream` with a Bearer token. this fork fakes Pro but has NO real server token, so Koodo's server rejects the request and it returns empty — upstream code just awaited it silently, leaving a blank translation panel. per user's loud-failure rule (global AGENTS.md rule 43), the patch does NOT substitute another engine. instead it checks whether `getTransStream` produced any text; if not, it shows a loud error toast + the error message in the translated panel ("Official AI Translation is a paid Koodo server feature. This fork has no valid server token..."). do not turn this into a fallback to google/libre/etc unless the user explicitly asks.
11. **first click on a cloud book downloaded it but opened nothing (2026-10-09)** = popup blocker. `BookUtil.redirectBook` (`src/utils/file/bookUtil.ts`) downloads the file first and only then calls `window.open(readerUrl)` — by then Chrome's transient user activation has expired, so `window.open` returns null (verified with a real trusted click: toast went "Downloading (0%)" → "Download successful", `window.open` call logged `blocked: true`, no tab). the fix (in the patch) reserves the tab *first*, synchronously in the click handler: `readerTab = window.open("", "_blank")`, then after the download sets `readerTab.location.href = readerUrl`; early-return paths (`no data source`, `Book not exists`, download failed) close the reserved tab so no blank tab is left behind, and if the tab itself was blocked/closed the reader fails **loudly** with a toast naming the book — no silent retry, no `location.href` fallback. if you touch this method, keep the reservation as the first statement (any `await` before it reintroduces the bug).
12. **reader routes + testing without the UI**: the reader is `#/<format>/<key>?title=<name>&file=<key>` (format = `epub`, `pdf`, `azw3`, … — see `src/router/index.tsx`). changing only `location.hash` does **not** remount the reader (same component instance for every format) — the page still shows the previous book until you `location.reload()`. for automation, the local library is IndexedDB `localforage` → store `keyvaluepairs` → key `books` (array of book models; count it to check a sync result — note there is also a stray empty `localforage-db` db name that a probe once created, it is not the app's), and the UI total reads `Total N books` on `#/manager/home`. cover clicks are what open a book — the title `<p>` is a **sibling** of `.book-item-cover`, so clicking the title does nothing.
13. **cloud-side edits got reverted on every sync (2026-10-09/10) - fixed in the patch; devices need one reload per deploy to get the new code**: the sync client cached its remote view for the whole page session (`SyncService.syncUtilCache` -> one megajs `Storage` whose node tree is snapshotted at login). edits made outside that tab (rclone pushes, another device) were invisible: reads resolved to dead nodes and returned `false` -> callers saw `"{}"` -> the merge concluded the cloud was EMPTY and uploaded the device's whole state over the cloud (verified: 3 `delete` records + 2 renames survived 5 min of polling, then a tab's sync at 10:30 and again at 11:37 restored all 41 rows and overwrote every record time; between 11:37 and 11:43 `sync.json` was missing entirely because the app deleted its stale node and the upload never landed). the same stale tree is why uploads created duplicate nodes (up to 11x `config.json`) - the adapter never saw its own previous uploads. four fixes now ship together: (a) `beforeSync` drops the cached client so every sync re-logs-in and re-lists the remote; (b) `getCompareResult` aborts LOUDLY (toast + throw) instead of pushing when cloud `sync.json` has no book records while cloud `books.db` still has rows; (c) newest-writer-wins pre-pass so a newer cloud `save` record pulls the cloud row (renames propagate to every device); (d) a read-failure probe before any cloud read (commit `670c9459`): with local records present, a throwing `remote.getRoot()` (session never connected - retried once after 1.5s) or a `sync.json`/`books.db` that the fresh `config` listing sees but `downloadFile` cannot return aborts the sync loudly. (d) exists because on the web path `downloadFile` collapses "connection/login failed" AND "file missing" into the same `false` - without the probe an empty read is indistinguishable from an empty cloud, and the merge then pushes the device's stale whole library over the cloud. that is exactly what the 2026-10-10 14:44:20 and 16:45:09 reverts were (both pushes carried the same 57 saves/6 deletes with pre-cleanup record times): fix (a)-(c) shipped at 12:39:58, but a transient MEGA login failure still produced an empty read and reverted the 12:41 and 16:37 cloud cleanups ~2h and ~8min later. **an old tab still running a pre-(d) bundle can still revert cloud edits - after deploying, reload every device once, then do cloud-side surgery, and verify the served `main.<hash>.js` matches the newest deploy.**
14. **UI still shows number-named / duplicate books after a clean sync (2026-10-10 "still numbers") - LOCAL ghost rows, not a cloud problem**: cloud can be perfectly clean (36 rows, correct records) while a device's IndexedDB `books` array holds ghosts, because (i) web `saveRecord` appended instead of replacing by key, so each pull of an already-present row left the stale copy next to the new one (one device held 42 rows with 3 copies of each renamed key), and (ii) rows whose local record already says `delete` were never removed once cloud+local records matched - the merge is a no-op and never queues deletes. the sync also takes ~1-3 min (repair walks the drive) and the UI only refreshes when it finishes, so checking 30 s after a reload always shows the old list. diagnosis: read IndexedDB `localforage` -> `keyvaluepairs` -> `books` (count + rows whose `name` is all digits) and `localStorage.syncRecord` (`database.sqlite.books.<key>` operations). fix: `BookUtil.reconcileLocalBookRows()` at sync start (dedupe by key + drop delete-recorded rows) plus replace-by-key `saveRecord` (commit of 2026-10-10 evening) - after this deploy every device self-heals on its next sync; instant one-off repair can also be done directly in the page via raw IndexedDB + `location.reload()`. **addendum (2026-10-10 late, desktop "after sync the number shows, before sync it doesn't")**: `repairBooksFromCloudFiles` re-indexes book FILES whose key is unknown locally, and MEGA's rubbish bin still holds the deleted binaries - the picker lists them under `book/` while rclone shows nothing at all (verified: rclone `book/` = 36, picker sees 38). repair also ran BEFORE `reconcileLocalBookRows` and stamped each resurrected row with save@now, so reconcile's drop rule (record = delete) could not drop it; the merge then re-adopted the cloud `delete` record but upstream `deleteRecord` leaves the row -> stable 38 rows + delete records, alternating 36/38 every other sync. fix: `reconcileLocalBookRows` now runs BEFORE the folder repair, and both repair loops skip keys whose sync record says `delete` (bundle markers `MEGA folder recovery skipped delete-recorded key` / `cloud book recovery skipped delete-recorded key`). the trashed binaries stay in the rubbish bin, inert; rclone cannot see or purge them, and no cloud surgery is needed.

15. **browser-use verification quirk on this machine (2026-10-11)**: Edge FREEZES a background tab that has been hidden for a while — timers, `fetch`, and IndexedDB callbacks in that tab never fire (only synchronous `Runtime.evaluate` + microtasks run, because CDP forces script execution). so an async `js("...")` hangs its full 5 s await cap and any fire-and-poll IDB read stays `null` even on a freshly reloaded document — freeze state is per-tab, reloads do not clear it. also, `js(expr)` without an explicit `target_id` resolves the harness's active session, which is ambiguous once a second tab exists: kick and poll can land on different tabs and `window` writes look "lost". reliable pattern: open a fresh **background** tab (`cdp("Target.createTarget", url=..., background=True)` — never activates, no focus steal), `switch_tab(target_id)`, and pass `target_id=<id>` to EVERY `js()` call; a new tab's callbacks work normally. keep that verification tab short-lived (close it when done) so two tabs never sync at once. end-to-end sync check: click `span.icon-sync` in the header (starts sync directly — status "Start Transferring Data (n/3)" → "Synchronisation successful"), then read `Total N books` and the raw `books` array.

16. **a cloud delete can be clobbered by a sync that was already running — and by record re-stamping (2026-10-13 "Meanwhile" duplicate round 2)**: cloud surgery at 23:29 (drop the duplicate row from books.db + flip its record save→delete) was uploaded over at 23:34 by the desktop tab's sync that had STARTED before the push — read-before/write-after. the merge itself would have honored the delete (`CompareDatabase`'s delete bucket is unconditional for local `save` + cloud `delete`), but that tab had read the pre-flip records, and the web path made it worse: `saveRecord`/`deleteRecord`/`updateRecord` wrote the whole `books` table via `saveAllRecords(..., isRecord=true)`, re-stamping EVERY row `save@now` on any single-row write — so the 23:34 upload carried all-`save` records and erased the delete. fixed in the patch (`isRecord=false` on the internal table writes; each method stamps only its own record). rules: (a) never push cloud surgery while a device's sync is in flight (visible as "Start Transferring Data (n/3)", takes ~1-3 min) — check the tab is idle first; (b) re-verify the flipped record ~1 min after pushing; (c) churn-free record times only exist after every device reloaded onto the post-2026-10-13 bundle.

## sync / MEGA data layout

- default sync option = MEGA (account `REDACTED_MEGA_ACCOUNT_EMAIL`, password in Bitwarden vault item `mega.nz - REDACTED_MEGA_ACCOUNT_HANDLE`)
- **TWO MEGA ACCOUNTS (2026-10-09, read this before touching the data)**: the app's account (`REDACTED_MEGA_ACCOUNT_EMAIL`, vault item `mega.nz - REDACTED_MEGA_ACCOUNT_HANDLE`) has its drive root at `KoodoReader/` + `config/` — everything below is **at account root**, no `/Root/` prefix. a *second* account is reachable only through rclone's persisted `[mega]` `session_id`/`master_key` in the default rclone.conf; its drive root is `Root/` + `github-mirror/`. `RCLONE_CONFIG_MEGA_TYPE/USER/PASS` env vars do **not** cancel that session, so any rclone call without an isolated `RCLONE_CONFIG` writes to the wrong drive and the site never sees the books. **always verify first**: `rclone lsf mega:/ --dirs-only` must print `KoodoReader/` + `config/`. the uploader (`automata-private\mega.nz\koodo-upload-book.py`) now uses an isolated temp config and fails loud otherwise.

- library metadata: `/KoodoReader/config/books.db` (sqlite, `books` table: key/name/author/md5/format/size). keys are millisecond timestamps (`Date.now()`).
- sync records: `/KoodoReader/config/sync.json` — book records named `database.sqlite.books.<key>` with `{operation:"save", time:<ms>}`. a book shows up in the app iff it's in books.db AND has a `save` (not `delete`) sync record.
- there's also a `/config/` folder (older sync base) — keep books.db + sync.json in sync across BOTH `/KoodoReader/config/` and `/config/` (symmetric), plus `/KoodoReader/book/` files.
- **megajs creates a duplicate node per upload**: same-name `sync.json`/`books.db`/`config.json` accumulate in those config dirs, and the app resolves them with `find(name === o)` (whichever node MEGA returns first) — a stale duplicate silently shadows a fresh one. purge duplicates (`rclone deletefile` in a loop until `rclone lsf` is clean) **before** pushing new config files.
- rclone is the CLI for MEGA here (megatools can't log in to this v3 account): `rclone lsf/lsl/copyto/deletefile mega:<path>` with `RCLONE_CONFIG` pointing at an isolated config (type/user/pass only). arg for forced overwrite: `--update` (see mega.nz AGENTS for the same-size-skip trap).

## settings & data persistence across deploys

settings live in two places, and deploys never touch either:

1. **app settings** (theme, font, layout, reading prefs, sync config) → browser localStorage, keyed to `https://koodoo.vercel.app`. each deploy replaces static files on Vercel — never touches user's browser. settings survive every deploy as long as the URL stays the same.
   - ⚠️ each Vercel preview URL gets a random subdomain (e.g. `koodo-reader-abc123.vercel.app`) — different origin, so it looks like a fresh app. always use the stable alias.
   - localStorage is cleared by: browser "clear site data" action, browser cache wipe, or switching browsers/devices. it does NOT survive those.

2. **library data** (books, reading progress, bookmarks, notes) → MEGA cloud at `/KoodoReader/config/books.db` + `sync.json` (and `/KoodoReader/book/<key>.<format>` files, older base `/config/`). this survives literally everything — deploys, browser switches, fresh computers — because it lives in the MEGA account (the *app's* account — see the two-account gotcha above). on a new browser, just connect MEGA sync and it pulls everything back.

**bottom line:** Vercel = just the app code (replaced each deploy). settings = browser + MEGA (never touched by deploys). the whole reason we set up the MEGA sync path is so user data outlives deploys.

## cloud book recovery gotcha

- Cloud book listings can remain stale after a duplicate is deleted. `BookUtil.redirectBook` attempts the file download directly; if that request fails, the binary for `<book.key>.<format>` is unavailable from the configured provider. The UI names the exact missing file/provider so it can be restored or re-uploaded instead of being mistaken for a routing bug.
- Two browsers/devices can import the same file concurrently while each has a different local database. The old import path generated a new timestamp key on both devices, and sync merged both rows because it compared keys rather than MD5. Imports now reuse the existing cloud book key; deleting one local duplicate also leaves its cloud binary untouched while another same-MD5 row remains.
- MEGA files are not enough to populate the library: Koodo needs both `config/books.db` and sync records. The sync startup now reconciles valid rows from cloud `books.db` when `sync.json` is missing or stale, so metadata uploaded before its sync record is no longer silently hidden.
- If a cloud `books.db` row is valid but a stale local `delete` record hides its metadata, sync now removes that stale delete and restores the cloud row. The download path reports a clear error if the binary itself is unavailable.
- If MEGA contains book binaries without `books.db` rows, sync indexes supported files by their remote basename, creates minimal metadata, and preserves that basename as the key so the existing download path can open the file.
- If users upload books from a second browser or directly into MEGA, the files may be outside Koodo's configured `book` folder. Browser sync now visibly labels "MEGA folder recovery", scans the root and ebook-related folders to a bounded depth, uploads supported files into the configured `book` folder, deletes the source only after upload succeeds, and creates non-NULL metadata rows. Do not broaden this into an unbounded full-drive scan.
- Files already in the configured `book` folder must be indexed in place; recovery must never re-upload/delete them just because they are missing from `books.db` or stale listing metadata.
- Recovery's extension filter must stay aligned with `supportedFormats` in `src/utils/common.ts`; Koodo also accepts `htm`, `xml`, `mhtml`, `docx`, and `md`, not only EPUB/PDF/ebook extensions.
